```python
import sqlite3 

def get_user(username): 
    conn = sqlite3.connect('users.db') 
    cursor = conn.cursor() 
    query = "SELECT * FROM users WHERE username='" + username + "';" 
    cursor.execute(query) 
    user = cursor.fetchone() 
    conn.close() 
    return user
```


---


The main weakness in this code is **SQL Injection**.

```sql
query = "SELECT * FROM users WHERE username='" + username + "';"cursor.execute(query)
```

The problem is that the SQL query is built by directly joining user-controlled input into the command string. If `username` contains malicious SQL syntax, the database may treat part of the input as SQL logic instead of simple data.

## Identified CWE

|CWE ID|CWE Name|Classification|Why it applies|
|---|---|---|---|
|**CWE-89**|Improper Neutralization of Special Elements used in an SQL Command / SQL Injection|Primary weakness|The code builds an SQL command using external input without safely separating data from SQL syntax. MITRE describes CWE-89 as a case where software constructs an SQL command using externally influenced input but does not correctly neutralize special elements that can change the command.|
|**CWE-20**|Improper Input Validation|Related weakness|The function accepts `username` without validating whether it has the expected format. MITRE defines CWE-20 as receiving input but failing to validate that it has the properties required for safe processing.|

## Security Implications

The most serious issue is that an attacker may manipulate the SQL query. Depending on the database structure and application behavior, this could allow them to retrieve another user’s record, bypass login-related checks, expose sensitive user data, or modify/delete database content if the query pattern is expanded elsewhere.

A simple attack scenario would be a login or user lookup form where the attacker enters crafted input instead of a normal username. Because the input is inserted directly into the SQL statement, the final query may no longer mean “find this username.” It may become a broader database command controlled partly by the attacker.

## Recommended Fix

Use **parameterized queries** instead of string concatenation. This keeps SQL logic separate from user input.

```python

import sqlite3

def get_user(username):
    conn = sqlite3.connect("users.db")
    cursor = conn.cursor()

    query = "SELECT * FROM users WHERE username = ?"
    cursor.execute(query, (username,))

    user = cursor.fetchone()
    conn.close()
    return user
```

With this version, `username` is treated as data, not as SQL code.

## Additional Security Controls

Validate the username before querying the database. For example, only allow expected characters and length, such as letters, numbers, underscores, and a reasonable maximum length.

Use least privilege for the database account. The application should not connect with an account that has unnecessary permissions such as deleting tables or modifying schema.

Avoid returning detailed database errors to users. Error messages should not reveal query structure, table names, or database internals.

For this snippet, the correct primary classification is **CWE-89: SQL Injection**. **CWE-20: Improper Input Validation** can be mentioned as a related contributing weakness, but the central vulnerability is SQL injection.
