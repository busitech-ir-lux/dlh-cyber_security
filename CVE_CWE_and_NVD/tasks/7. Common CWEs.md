## Common CWE examples and their impact

**CWE** helps us describe common weakness patterns in software. These weaknesses can later become real vulnerabilities if they are not fixed.

MITRE’s CWE project describes CWE as a community-developed list of software and hardware weaknesses that can become vulnerabilities. The CWE Top 25 also highlights common and impactful weaknesses that are often easy to find and exploit. ([CWE](https://cwe.mitre.org/?utm_source=chatgpt.com "Common Weakness Enumeration: CWE - MITRE"))

|CWE|Weakness|Simple meaning|Potential impact|
|---|---|---|---|
|**CWE-79**|Cross-Site Scripting, XSS|The application allows unsafe content into a webpage|Account hijacking, stolen cookies, fake pages, user data exposure|
|**CWE-89**|SQL Injection|User input is inserted into database queries unsafely|Data theft, data modification, authentication bypass|
|**CWE-787**|Out-of-bounds Write|Software writes data outside the correct memory area|Crash, remote code execution, system compromise|
|**CWE-798**|Hard-coded Credentials|Passwords or keys are written directly in code|Unauthorized access if the code or binary is exposed|
|**CWE-287**|Improper Authentication|The system does not properly verify identity|Attackers may log in as other users or bypass login|
|**CWE-862**|Missing Authorization|The system does not check whether a user is allowed to perform an action|Users may access admin functions or sensitive data|
|**CWE-20**|Improper Input Validation|The application does not properly check user input|Injection, crashes, unexpected behavior|
|**CWE-352**|Cross-Site Request Forgery, CSRF|A user is tricked into performing an unwanted action while logged in|Unauthorized account changes, unwanted transactions|

## How to prioritize these weaknesses

A software team should not treat all CWEs equally. Some weaknesses are more dangerous depending on where they appear and what they affect.

### 1. Fix critical impact weaknesses first

Start with weaknesses that can lead to:

- remote code execution
- authentication bypass
- privilege escalation
- sensitive data exposure
- full system compromise


For example, **CWE-787**, **CWE-89**, **CWE-287**, and **CWE-862** should usually receive high priority because they can seriously damage confidentiality, integrity, or availability.

### 2. Prioritize internet-facing features

A weakness in a public login page, API, payment system, or web server is more urgent than the same weakness in an internal test tool.

For example, SQL injection in a public search form should be fixed quickly.

### 3. Consider exploitability

Ask:

> “How easy is this to exploit?”

If the weakness is easy to exploit and does not require authentication, it should move higher in priority.

### 4. Consider business impact

A weakness in a system that handles customer data, financial data, credentials, or medical records should be treated as more serious.

### 5. Use tools and reviews together

Static analysis tools, dependency scanners, penetration testing, and code review can help find CWE-related weaknesses. But tools alone are not enough. Developers should also use CWE as a checklist during design and code review.

## Simple prioritization model

A practical order could look like this:

1. **Remote code execution and memory corruption weaknesses**
2. **Authentication and authorization weaknesses**
3. **Injection weaknesses**
4. **Hard-coded secrets and credential exposure**
5. **Input validation and output encoding issues**
6. **Lower-impact information leaks or configuration issues**


## Simple summary

Common CWEs show the types of mistakes that often lead to security vulnerabilities. In a software project, teams should prioritize weaknesses based on real risk: impact, exploitability, exposure, and business importance. The goal is not only to fix bugs, but to remove the patterns that create vulnerabilities in the first place.
